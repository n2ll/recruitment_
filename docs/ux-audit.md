## 2. A. 가장 시급 (운영 사고·데이터 손실 직결)

### A-1. 로드 실패가 "데이터 없음"으로 위장 — 구조적 결함 `[열림]`

거의 모든 데이터 로더가 `catch { console.error }`만 하고 빈 배열을 유지한다. 네트워크/서버 오류 시 화면에 "후보 없음 / 지원자 없음 / 대화 없음 / 미분류 없음"이 떠서, 매니저가 **실재하는 데이터를 없다고 오판**한다. 실 DB로 진행하는 시연에서도 위험.

현재 위치(검증):
- `app/admin/page.tsx` — `fetchData` `:560-571`, `fetchBranches` `:783-793`, `fetchHeartbeats` `:799-807`, `openChat` `:837-856`
- `DanggeunView.tsx` — `:333-334`(목록), `:356-357`(대화)
- `AgentJobsView.tsx` — `:88`(공고), `:102`(후보), `:119`(대화)
- `PendingInboxView.tsx` — `:38-41` (`if (res.ok)` else 무처리 + catch console.error)
- `PromptExamplesView.tsx` — `:85`

영향: 데이터 누락 인지 불가 → 잘못된 재발송·중복 등록·놓친 처리.
권장: 에러 state를 빈 state와 분리. "불러오지 못했어요 · 다시 시도" 배너 + 재시도 버튼. (PendingInbox는 이미 새로고침 버튼·로딩이 있으나, 실패를 여전히 빈 상태로 표시하므로 동일 처리 필요)

### A-2. 종료성 상태 무확인 변경 `[부분]`

`부적합`/`이탈`로 바꾸면 즉시 PATCH되고 파이프라인에서 빠진다. 실수 시 복구하려면 다른 화면으로 이동해야 함.

- `[해결] DanggeunView.tsx:529-540` — `handleStatusChange`가 `부적합/이탈`에 한해 confirm("종료성 상태라 파이프라인에서 빠집니다") + `statusSaving` 비활성(`:754`) 적용됨.
- `[열림] app/admin/page.tsx:1349-1357` — 지원자 목록 테이블의 인라인 상태 `<select>`는 여전히 `onChange → patchApplicant` 즉시 호출(낙관적 업데이트), confirm 없음.

권장: 지원자 목록 인라인 셀렉트도 종료성 상태 전환 시 확인 + "목록에서 숨겨져요" 안내(DanggeunView와 동일 패턴 이식).

### A-3. 실 SMS가 확인 없이/오타로 발송 `[부분]`

- `[해결] JobCreateModal.tsx:176-182` — `공고 SMS 일괄 발송`에 confirm("실제 문자가 즉시 나갑니다. 진행할까요?") 추가됨.
- `[해결] app/admin/page.tsx:532` — 추천 일괄 발송은 `confirm("N명에게 SMS 발송하시겠습니까?")` 존재.
- `[열림] AgentJobsView.tsx:468-473` — 패널 textarea가 `placeholder="...(Enter 발송)"`, Enter(Shift 제외) 시 확인 없이 실 SMS(`sent_by:"관리자"`). 작성 중 Enter 오타 = 오발송.
- `[열림(경미)] DanggeunView.tsx` 매니저 직접 발송 — 채팅 UX 특성상 확인 없음(`Cmd/Ctrl+Enter`). 비가역·비용이라 최소한 단축키 안내 권장.

권장: 1:1 발송은 Enter=줄바꿈/버튼=발송 분리 또는 첫 발송 확인. 일괄 발송 카운트는 A-3과 별개로 C-16 참조.

### A-4. confirm "취소"가 취소가 아니라 다른 동작 실행 `[해결]`

이전: `confirm("스크리닝으로 재개?\n(취소=온보딩으로 재개)")` — 닫으려는 취소가 온보딩 재개를 실행(자동 발송 부수효과 위험).
현재: `AgentJobsView.tsx:980-989` — `window.prompt`로 `1=스크리닝 / 2=온보딩 / 빈칸·취소=아무 작업 안 함`으로 변경됨. **함정 제거.** 다만 native `prompt` 사용은 C-15(다이얼로그 톤)로 흡수.

### A-5. 일시정지·단계변경·재개 버튼 로딩/중복클릭 방지 부재 `[부분]`

- `[해결]` 상태 셀렉트: `statusSaving`으로 비활성(`DanggeunView.tsx:754`).
- `[열림] DanggeunView.tsx` — `⏸ AI 일시정지`(`:768-797`), 단계 변경 `onStageClick`(`:802-827`), `▶ AI 응답 재개`(`:845-875`) 세 버튼은 confirm은 있으나 fetch 진행 중 `disabled`/로딩 표시가 없음. 응답 지연 시 재클릭 → `set-stage` 중복 발송 위험. (참고: `handleSendReply`는 `sendingRef` 가드 있음 / `AgentJobsView`는 `busy` prop으로 가드)

권장: 세 버튼에 진행 중 `disabled` + "처리 중…" + ref 가드 추가.

## 3. B. 지원자 폼(`/apply`)

### B-6. 마케팅 수신 동의 기본 체크(opt-out) `[열림]` — 법적 리스크

`app/apply/page.tsx:181` `marketingConsent: true`. 국내 정보통신망법상 마케팅 수신 동의는 **기본 미체크(opt-in)**가 원칙. 1줄 수정이며 신뢰·컴플라이언스 직결.
권장: 기본값 `false`.

### B-7. 검증이 제출 시점에만 동작 `[열림]`

`:225-248` `validate()`는 제출 시 한 번에 검사, 실패하면 첫 `.error-msg`로 스크롤만(`:251-255`). 6섹션 단일 스크롤 폼이라 진행 표시·필드 blur 검증이 없어 좌절 유발.
권장: 진행 표시(또는 멀티스텝) + blur 단위 검증 + 상단 에러 요약. (리디자인 플랜 `p1-apply`가 멀티스텝/진행바를 다루므로 그쪽에 흡수)

### B-8. "본인 명의 문제 있음" 막다른 길 `[열림]`

`:243-245`, `:552-560` 선택 시 `alert`만 뜨고 버튼은 선택된 채 빨간 에러로 영구 차단. 화면상 다음 행동 안내 없음.
권장: 인라인 안내 + 대안(문의/매니저 연결) 제시. native alert 지양.

### B-9. 제출 실패가 통짜 alert `[열림]`

`:268` `alert("제출 중 오류가 발생했습니다...")`. 중복지원/서버오류 구분 없음. (입력값은 state 유지됨)
권장: 실패 사유 구분 + 재시도 안내, 토스트/인라인 배너.

### B-10. 커스텀 드롭다운·라디오 키보드/스크린리더 비대응 `[열림]`

`:100-157` `Dropdown`이 `div` 기반(role/tabIndex/aria/방향키 없음). 라디오는 실제 `<button>`이라 그룹으로 안 읽힘.
권장: 네이티브 `select` 또는 접근성 갖춘 컴포넌트(리디자인의 shadcn `Select`로 자연 해소 가능).

## 4. C. 매니저 대시보드 (중간)

### C-11. 반응형 대응 거의 전무 `[열림]`

어드민 전체에서 `@media`가 2곳뿐. 좌우 분할 패널·고정폭(칸반 6열 고정, 상세/패널 380~440px 고정)이라 좁은/분할 화면에서 레이아웃 붕괴·가로 스크롤. `DanggeunView`/`AgentJobsView`/`PlaygroundView` 미디어쿼리 0개.
권장: 특정 폭 이하 단일 컬럼 전환. (리디자인 Tailwind 전환이 근본 해소 — `verify`에 반응형 체크 포함 권장)

### C-12. 편집 중 이탈 시 입력 소실(경고 없음) `[열림]`

- `ApplicantFormModal.tsx:144` 배경 클릭 → 6섹션 입력 전부 소실(`onClick={onClose}`).
- `JobCreateModal.tsx:248` 동일(`onClick={onClose}`) — 긴 공고 본문/선택 소실.
- `app/admin/page.tsx:1434` 상세 패널에서 다른 섹션 "편집" 누르면 직전 섹션 미저장분 조용히 취소.
- `app/admin/page.tsx:1449` "변경됨" 태그가 떠도 `← 목록으로` 시 확인 없이 폐기.

주의: 리디자인에서 shadcn `Dialog`로 옮기면 **오버레이 클릭 닫힘이 기본값**이라 그냥 마이그레이션 시 이 버그가 유지됨.
권장: 입력값 존재 시 닫기/이탈에 확인. 모달은 dirty 시 오버레이 닫힘 비활성.

### C-13. 대화창 자동 스크롤이 과거 읽기 방해 `[부분]`

- `[해결] DanggeunView.tsx:432-434` — "다른 대화를 새로 열거나 사용자가 하단 근처일 때만" 스크롤하도록 보강됨.
- `[열림] app/admin/page.tsx:2746` — 대화 패널이 `ref={(el)=>{ if (el) el.scrollTop = el.scrollHeight }}`로 **매 렌더 강제 최하단**. 위로 올려 과거를 읽는 중 새 메시지 시 점프.

권장: page.tsx 대화 패널도 "하단 근처일 때만" 로직 적용.

### C-14. 안 읽음 배지가 대화 열어도 안 줄어듦(당근 뷰) `[열림]`

`DanggeunView.tsx:672` 후보 선택은 `setSelectedId`만 호출 — 읽음 처리/배지 초기화 없음. (메인 `page.tsx`의 `openChat:847-850`은 `unread_count` 0으로 초기화 → 그쪽은 정상)
권장: 당근 뷰 선택 시 낙관적 0 처리 또는 읽음 API 호출.

### C-15. native alert/confirm/prompt 전면 사용 `[열림]`

거의 모든 액션이 브라우저 기본 다이얼로그. 앱 톤과 동떨어지고 흐름을 끊으며, 카피 톤 룰(`20-copy-tone`: "오류가 발생했습니다 → SMS 발송에 실패했어요 · 다시 시도")에 어긋남. 사유 입력에 `prompt()` 사용(`AgentJobsView.tsx:976`/`:981`/`:993`)은 멀티라인·검증 불가.
참고: confirm 자체가 잘못은 아님 — 일부는 안전장치로 적절(§5). 문제는 "톤/스타일 제어 불가 + 모호한 메시지".
권장: 공용 toast/Dialog로 통일 + 도메인 명사 + 다음 행동 제시. (리디자인 `p0-primitives`에 흡수)

### C-16. 발송 대상 카운트 ≠ 실제 발송 수 `[열림]`

`JobCreateModal.tsx` — 버튼/카운트는 `selected.size` 기준이나, 실제 발송은 `source==="applicant"`만(`:208-214`). 레거시 후보가 선택돼 있으면 본 숫자와 실제 발송 건수가 어긋나고, 레거시만 선택 시 발송 직전에야 "발송 가능한 신규 후보가 없습니다"로 실패.
